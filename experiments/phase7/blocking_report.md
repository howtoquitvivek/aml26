# Phase 7: Blocking Recall Analysis

## 1. Authoritative Baseline
Tested using the standard validation split (220,683 S1 entities) and the frozen Phase 6 blocking logic (`CFG1_NoTwoTok_KeyE`, Top K=100).

- **Blocking Recall:** 74.25%
- **Total Candidates:** 10,016,298
- **Avg Cands/S1:** 45.38
- **Median | P95 | Max:** 27 | 100 | 100
- **Zero-candidate S1s:** 3,025
- **Missed GT Links:** 196,621

## 2. Blocker Inspection Findings
- The candidate extraction logic unconditionally queries all configured keys (Exact, Canonical, Address Num+NamePrefix, KeyB, KeyE).
- **There is no logic that suppresses address querying when name candidate sets are large.** Address candidates are always retrieved.
- However, all retrieved candidates are merged into a single pool, scored by static weights, and then truncated by the global `K=100` budget limit. 

## 3. Experiment Results

### A. Name UNION Address (Independent Budgets)
To test if address candidates were being pushed out of the Top 100 by large name candidate sets, we gave Name and Address independent budgets of K=100 each (Max 200/S1).
- **Recall:** 74.26% (+0.01%)
- **Total Candidates:** 11.34M (+1.3M)
- **GT Links Recovered:** 141
- **Conclusion:** Address candidates are NOT being suppressed by name candidates. The existing address keys simply aren't retrieving these missed links.

### B. No Suppression (K = Unlimited)
We removed the K=100 budget entirely, allowing all candidates generated by the current keys to pass through.
- **Recall:** 80.14% (+5.89%)
- **Total Candidates:** 27.86M (+17.8M)
- **Avg Cands/S1:** 126.25 (Median: 27, P95: 580, Max: 3237)
- **GT Links Recovered:** 45,025
- **Conclusion:** The current keys *are successfully retrieving the missed links*, but they are being mercilessly truncated by the rigid `K=100` cutoff!

### C. Strong Address Composites (Add ZIP/PIN Key)
Added a simple ZIP/PIN code blocking key (last numeric token).
- **Recall:** 74.32% (+0.07%)
- **Total Candidates:** 14.49M (+4.4M)
- **GT Links Recovered:** 565
- **Conclusion:** Poor tradeoff. Added 4.4 million candidates for virtually zero recall gain. 

## 4. Decision Gate Recommendation

**Recommendation: Keep Current Blocker Keys, Move to Priority 2 (K Optimization)**

The evidence unequivocally shows that adding new address keys (Exp C) or forcing address unions (Exp A) provides negligible value. The true bottleneck is not the *retrieval* keys, but the **K=100 budget truncation**. 

By simply removing the K limit (Exp B), we recover **45,025 true matches** and boost recall by **~5.9% absolute**. The cost is 27.8M total candidates. Since 27.8M candidates average out to 126 per S1 and peak at ~3200, this is extremely manageable for our XGBoost inference pipeline (which easily handles ~7.8GB RAM for 54M candidates on the 1.7M test set). 

The evidence strongly supports moving immediately to Priority 2: Optimizing the K threshold (e.g., K=200, K=500, or K=unlimited).
