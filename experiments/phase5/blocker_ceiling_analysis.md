# Phase 5A: Blocker Ceiling Analysis

The `CFG1_NoTwoTok_KeyE` blocking framework yielded an 80.27% ceiling (meaning 19.73% of Ground Truth links were missed by the keys). However, an in-depth analysis of the pipeline flow across the 220,683-S1 validation set revealed a critical, two-stage failure mechanism.

## 1. The Anatomy of the 32% "Matcher Deprivation"
Although the keys generated 80.27% of the truth set, the matcher only evaluated 67.97% of the truth set. 
Out of the 763,592 Ground Truth pairs in the full validation set:
- **Never Generated by Keys:** ~150,000 pairs (19.7%) were completely missed by the exact, canonical, AddrOld, KeyB, and KeyE indices.
- **Dropped by Top-25 Budget:** ~94,000 pairs (12.3%) were generated by the keys, but were ranked below the top 25 by the heuristic weighting function, meaning they never reached the Logistic Regression model.
- **Rejected by Logistic Regression:** ~47,500 pairs (6.2%) reached the LR model but were scored below `0.80`.
- **Successfully Matched:** ~471,600 pairs.

*Insight:* The Logistic Regression model actually possesses a **90.8% recall** on the Ground Truth pairs it was permitted to see! The primary bottleneck is the blocker/budget.

## 2. Analysis of the 244,513 Pre-Matcher Misses

An analysis script extracted the string bodies for all 244,513 missed/dropped GT pairs and calculated heuristic flags:

| Miss Category | Percentage | Interpretation |
| :--- | :--- | :--- |
| **High Address Char Overlap** | 77.53% | Vast majority share very similar addresses but miss `AddrOld` (requires exact match) and `KeyE` (requires 2 digits). |
| **Shared Numbers** | 64.47% | 64% of misses share at least one digit sequence, but it wasn't enough to trigger Key E. |
| **High Name Char Overlap** | 58.56% | Minor typos or OCR errors in the Latin script. Because `KeyB` requires the first 3 letters to be exact, typos in the prefix cause complete retrieval failure. |
| **Cross-Script / Transliteration** | 21.92% | Entirely different alphabets (e.g., Latin vs Devanagari). These yield ~0% character overlap, rendering all lexical blocking keys completely useless. |
| **India Misses vs US Misses** | 53% IN / 47% US | The Indian dataset is disproportionately harder to block due to transliteration and unstructured addresses. |

## 3. Proposal and Evaluation of New Blocking Keys

To address the lexical typo misses, we designed and simulated three new heuristic blocking keys over the 10,000-S1 holdout set, indexing the entire S2/S3 catalog to measure explosion risk:

**1. `Key_Consonants`** (First 4 sorted consonants of canonical name + country)
- **Goal:** Bypass prefix typos and vowel swaps.
- **GT Recovered (10k holdout):** 4,248 pairs
- **Explosion Risk:** Avg 12,719 cands/S1 | P95: 45,400 | Max: 220,713
- *Verdict:* Highly effective at recovering recall, but too explosive. Bypasses the 10,000 candidate budget limit we established in Phase 3.

**2. `Key_AddrAlpha`** (First alphabetic word >= 4 chars in address + country)
- **Goal:** Exploit the 77% address overlap.
- **GT Recovered:** 6,650 pairs
- **Explosion Risk:** Avg 58,125 cands/S1 | P95: 261k | Max: 724,757
- *Verdict:* Catastrophically explosive due to common address words like "Shop", "Near", or "Road".

**3. `Key_NameNum`** (First exact numeric token in name + country)
- **Goal:** Match numbered branches (e.g. "Store 14").
- **GT Recovered:** 116 pairs
- **Explosion Risk:** Avg 2,121 cands/S1 | Max: 6,640
- *Verdict:* Safe, but provides negligible recall lift.

## 4. Final Recommendations for Phase 5

The empirical data proves that adding more lexical keys (like `Key_Consonants`) inevitably leads to the same candidate explosion problems we saw with `TwoTok`, without solving the fundamental cross-script boundary (which accounts for ~22% of all misses). Furthermore, ~94,000 pairs are already being retrieved by the current safe keys but are simply being truncated by the Top-25 limit.

**Recommended Next Experiments (Phase 5B):**

1. **Expand the Budget Limit:** Before writing new keys, we should increase the Top-K ranking budget from `25` to `75` or `100`. Because feature extraction is currently taking only ~4.5 minutes for 3.7 million candidates, the pipeline can easily afford evaluating 10 million candidates. This requires zero new code and immediately recovers the 94,000 dropped pairs.
2. **Move to Non-Lexical Blocking for India:** Since 22% of misses are Cross-Script (Devanagari vs Latin), we cannot rely on string-matching keys. We must experiment with **Cross-Lingual Embeddings (e.g., LaBSE, FastText, or SentenceTransformers)** for the blocker, utilizing a fast Approximate Nearest Neighbor (FAISS) index to retrieve transliterated candidates.
3. **Upgrade Matcher to XGBoost:** The LR model performs admirably, but XGBoost can better capture non-linear relationships (e.g., heavily weighting Address Jaccard ONLY when Name Jaccard is 0 due to cross-script).
